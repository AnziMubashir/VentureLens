# MASTER DEVELOPMENT PROMPT — VENTURELENS

You are acting as a senior software architect, product designer, and full-stack AI engineer. Your responsibility is to design and build the initial working version of VentureLens, a professional multi-agent AI-powered idea evaluation platform.

This is a serious software engineering project. Do not approach it as a generic academic assignment or a simple AI chatbot.

## 1. Project Overview

**Product:** VentureLens  
**Tagline:** See your idea from every angle.

VentureLens is an AI-powered virtual boardroom that helps individuals evaluate, refine, and present early-stage startup, product, and software ideas.

The platform uses three specialized AI agents, coordinated by a central Main Agent, to evaluate ideas from different perspectives. A second-stage challenge process allows agents to critically examine assumptions and recommendations before producing the final deliverables.

The two primary deliverables are:
1. A comprehensive Boardroom Report.
2. A professionally designed static pitch website.

Both deliverables MUST be generated from the same refined analysis to maintain consistency.

I will provide the original CS325 Software Engineering Assignment 02 PDF. Treat that document as the primary source of project requirements. Preserve its intended scope and functionality. Where implementation details are unspecified, make reasonable engineering decisions and document them explicitly.

## 2. Core Functional Requirements

### A. Idea Submission

Build a polished idea-submission interface that collects:

- Idea name.
- Idea description.
- Problem being solved.
- Target users.
- Proposed solution.
- Optional additional context, constraints, and assumptions.

Validate inputs and provide helpful guidance.

### B. Specialized AI Agents

Implement three genuinely distinct agents.

**1. Investor Agent**

Responsible for business and commercial evaluation.

It must assess:
- Market and value proposition.
- Customer need.
- Potential revenue models.
- Competitive differentiation.
- Commercial and market-related risks.

**2. Technical Agent**

Responsible for technical feasibility.

It must assess:
- Technical feasibility.
- Recommended technologies and infrastructure.
- Development complexity.
- Security and scalability concerns.
- A realistic, appropriately scoped MVP.

**3. User Agent**

Responsible for user-centric evaluation.

It must assess:
- Target users and their pain points.
- Practical user value.
- Adoption barriers.
- Important user-facing features.
- User experience considerations.

Each agent must have its own clearly defined system instructions, responsibilities, output schema, and analytical approach.

Do not implement three cosmetic agents that simply return differently formatted versions of the same generic LLM response.

### C. Main Agent — Board Chair

The Main Agent is the central orchestrator.

Its responsibilities include:
- Coordinating the three specialized agents.
- Managing their execution.
- Collecting structured outputs.
- Identifying agreements and disagreements.
- Identifying dependencies between recommendations.
- Producing a coherent consolidated evaluation.

The Main Agent should preserve the individual agents' findings rather than blindly accepting or averaging their recommendations.

### D. Challenge My Idea

This is a particularly important feature.

After the initial evaluation, introduce a second analytical stage.

The specialized agents should critically examine relevant findings and recommendations from the other agents.

Examples:
- The Investor Agent recommends mandatory user verification.
- The Technical Agent examines the infrastructure, security, and implementation implications.
- The User Agent identifies privacy concerns, friction, and potential adoption barriers.

The Main Agent subsequently synthesizes these challenges.

The output should identify:
- Challenged assumptions.
- Contradictory recommendations.
- Overlooked risks.
- Trade-offs.
- Recommendations requiring revision.
- Areas of agreement.

This must be a distinct second stage, not merely another generic summary generated by the Main Agent.

### E. Boardroom Report

Generate a professional, structured report containing:

- Executive summary.
- Original idea overview.
- Business evaluation.
- Technical evaluation.
- User evaluation.
- Cross-agent findings.
- Strengths.
- Critical weaknesses and risks.
- Challenge My Idea findings.
- Refined recommendations.
- Proposed MVP and its essential features.
- Development priorities.
- Future opportunities.
- Final synthesized assessment.

The report must be readable, well-formatted, and suitable for presentation or export.

### F. Static Pitch Website

Generate a professional, visually appealing static pitch website using the refined analysis.

Potential sections:
- Product name and value proposition.
- Problem.
- Solution.
- Target users.
- Core features.
- Competitive differentiation.
- Business proposition.
- MVP.
- Future vision.

The website must use the same underlying refined analysis as the Boardroom Report.

It must be a presentation website, not a functional implementation of the submitted startup idea.

## 3. Technical Architecture

Before implementation, evaluate suitable technology choices.

Consider:
- Frontend: React / Next.js with TypeScript.
- Backend: Python with FastAPI, or another justified alternative.
- Agent orchestration: Evaluate Google Agent Development Kit (ADK), LangGraph, and other suitable agent frameworks.
- LLM: Gemini models, with a clean provider abstraction where practical.
- Data validation: Structured schemas such as Pydantic or equivalent.
- Styling: Tailwind CSS or an equally suitable design system.

Do not select technologies merely because they are popular. Explain your selections based on project requirements, maintainability, integration complexity, and demonstration reliability.

The architecture must support:
- Independent specialized agents.
- Main Agent orchestration.
- Structured agent-to-agent information exchange.
- A distinct challenge stage.
- Shared final analysis.
- Report and website generation.

Prefer parallel execution of independent initial agents where appropriate.

Implement genuine multi-agent behavior using the selected framework. Do not simulate multiple agents through a single LLM call with different headings.

Keep model calls and agent responsibilities modular so the LLM provider can be changed without rewriting the entire application.

**API and credential requirements:**
- Never hardcode API keys.
- Use environment variables.
- Provide `.env.example`.
- Ensure `.env` is excluded through `.gitignore`.
- Keep all model calls on the backend.
- Never expose API credentials to frontend code.

Provide a demonstration mode with deterministic sample/mock agent outputs so that the complete workflow can be demonstrated even if API access, quotas, or network connectivity become unavailable.

Clearly distinguish demonstration mode from live LLM mode. Do not present mock outputs as real AI analysis.
